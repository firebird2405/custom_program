### 점수를 올리는 조치

- 검색을 전 보드로 확장한다. discoverBoards()+readStore() 로 다른 보드의 저장분까지 훑어 '다른 보드에서 N건'을 툴바에 띄우고, 클릭하면 그 보드로 전환하며 해당 노트를 맨 앞으로 올린다. switchBoard 진입 시 searchBox 를 비우는 한 줄을 함께 넣는다.
- 검색 상태를 화면에 쓴다 — 매치 수 표시, 결과 0 일 때의 안내 문구, .pnote.dimmed 에 pointer-events:none 추가, 매치는 z 를 올려 앞으로 승격.
- 보드 줌아웃(또는 보드 스크롤)을 D+30 에서 이번 판으로 끌어올린다. #board 에 CSS transform: scale() 한 겹과 슬라이더 하나만으로도 50장을 한 화면에서 조망할 수 있고, 현재의 24px 슬리버 계단을 실제 해법으로 바꾼다.
- 정리 배치의 계단 띠를 전역 maxW/maxH 가 아니라 항목별 크기로 계산해 큰 노트 한 장이 나머지 배치를 무너뜨리지 않게 한다(5226-5231).

### 검증관 판정

인용 근거는 전부 확인됐다 — #board position:fixed;inset:0(30-32), applySearch 가 활성 보드 data 만 순회(4990-4997), .dimmed 에 pointer-events 없음(358), switchBoard 가 검색어를 비우지 않고 loadBoard 가 applySearch 를 재호출(6927-6947, 6949-6974), 회수 상한 maxX = bw - RESCUE_GRIP_PX(5437-5451). 그런데 수용량 추정이 낙관적이다 — 셸은 창 높이 860 에서 프레임과 TABBAR_HEIGHT 40 을 빼고 뷰를 배치하므로(electron/main.js:201, 680-681) 실제 보드 높이는 약 789px 이고, 툴바가 한 줄만 늘어도 shelfBottom(4248-4258)이 내려가 4행이 3행(≈21장)으로 떨어진다. 더 심각한 미포착은 사진 전용 노트다 — applySearch 가 n.text 만 보므로(4993) 본문이 빈 사진 메모는 어떤 검색어에도 항상 opacity 0.22 로 흐려져 '사진이 사라졌다'로 읽힌다. 발주 #22(정리)와 #29(창 크기)는 이미 작업 트리에 반영돼 scoreNow 에 포함된 상태이고 #23~#31 중 적재·검색·조망을 건드리는 것은 없으므로 scoreAfter 는 사실상 scoreNow 와 같다.

**채점자가 놓친 근거**

- postit.html:4990-4997 — hit 판정이 n.text 만 본다. 본문이 빈 사진 전용 노트는 어떤 검색어에도 매치가 되지 않아 항상 .dimmed 로 남는다. 사진 메모를 쓰라고 권하는 제품(우클릭 '사진 넣기', 6424-6427)에서 검색 한 번이 그 메모들을 통째로 지워진 것처럼 보이게 한다.
- electron/main.js:201 · 680-681 — TABBAR_HEIGHT = 40 이고 layoutViews 가 뷰 높이를 contentBounds.height - top 으로 준다. 창 높이 1280×860 에서 실제 보드 높이는 프레임+탭바를 뺀 약 789px 이며, 설정 드로어가 열리면 SETTINGS_DRAWER_HEIGHT 만큼 더 줄어 수용량이 한 행 더 깎인다.

- postit.html:4309-4313 — 보드가 가득 찼을 때 findSpawn 은 겹침 검사를 포기하고 모듈로 좌표를 반환한다. 50장 상태에서 새 메모는 기존 메모 위에 생기며 경고나 안내가 없다.
- postit.html:5437-5451 — rescueLimits 의 minX 는 44 - w 로 폭을 반영하지만 maxX 는 bw - 44 로 폭을 무시한다. 즉 왼쪽 이탈만 폭 기준으로 판정되고 오른쪽·아래 이탈은 44px/34px 만 걸치면 회수 대상에서 빠진다. 채점자의 I3 근거 '회수 판정이 n.x·n.y 만 본다'는 좌측에 한해서는 부정확하나 결론(오른쪽 가장자리 노트는 영구 미회수)은 성립한다.

- 일정 검색 입력과 연·월 점프를 넣는다 — monthTitle(calendar.html:718)에 클릭 리스너를 달아 연/월 선택을 띄우고, 헤더 [보기] 그룹에 검색 입력을 추가해 events + repeats 를 한 번에 훑게 한다. 두 기능 모두 신규 저장 키 0개로 구현된다

### 검증관 판정

## I8 저장 한계 — 5MB 천장·조용한 실패·IDB 무언 강등

> 채점자 원안 62/64 → 검증관 하향 **52/54**

캘린더는 저장 실패를 전용 배너로 끝까지 알리는 수준에 도달했지만 포스트잇은 같은 경고를 바로 다음 성공 토스트가 덮어 버려서, 사용자는 천장에 처음 닿는 순간인 사진 첨부에서 데이터를 잃고 있다는 사실을 통보받지 못한다.

### 근거

- calendar.html:709, 1085-1099, 1146-1163 — 저장 실패가 토스트가 아니라 전용 지속형 배너 #saveBanner(role=alert, aria-live=assertive)로 뜬다. fail>warn 랭크로 낮은 단계가 덮지 못하고, 복구되면 자동 회수되며, 감사가 지적한 saveErrorShownFor 세션 1회 억제는 키별 30초 쿨다운으로 교체됐다. 이 부분은 이미 상업 수준이다.
- postit.html:2564-2570, 2572-2598 — 포스트잇도 실패 디듀프(30초)와 80/90% 선제 경고를 갖췄고 90% 문구는 '사진 메모는 더 못 붙여요'로 결과를 명시한다. calendar.html:1112-1130 도 동일하게 80% 토스트·90% 배너를 낸다.
- postit.html:2471-2497 — 그러나 포스트잇의 실패 안내는 showNoticeCore 가 쓰는 단일 토스트 엘리먼트를 모든 안내와 공유한다. dur≤0 의 '지속형'은 다음 showNotice 호출 한 번으로 사라진다.
- postit.html:6152-6153 — 사진 첨부는 saveNow() 직후 showNotice('사진을 붙였어요.')를 호출한다. 용량 초과로 저장이 실패해 notifySaveFailure 가 띄운 지속형 경고가 이 성공 문구에 즉시 덮인다. 같은 패턴이 4199-4200(날짜 지정), 5398-5400(정리 되돌리기) 등 saveNow 호출 29곳 곳곳에 있다.
